3.3.2 Join Condition

EBAN INNER JOIN T001W ON T001W-WERKS = EBAN-WERKS INNER JOIN T001K ON T001K-BWKEY = T001W-BWKEY. Both joins are on full primary keys (WERKS, BWKEY), so each EBAN row matches exactly one row and there's no fan-out. Verified mapping: plants 1000/1100/1200/1300 → company code 1000; 3000/3200 → company code 3000.

3.7 Processing Logic

Design for testability. START-OF-SELECTION only builds the selection structure, creates the processor with injected dependencies, calls run and displays the result. All database access sits behind lif_data_access and RFQ creation behind lif_rfq_creator. ABAP Unit uses classic dependency-injection fakes; CL_OSQL_TEST_ENVIRONMENT is not used because it isn't available on SAP_BASIS 740.

Step 1 – INITIALIZATION. gv_tit1..4 = block titles; P_ANGDT = sy-datum + 14; P_RFQTY = 'AN'; P_TEST = 'X'.

Step 2 – AT SELECTION-SCREEN. Build ty_selection from the screen fields. lcl_processor->validate_selection runs V1–V7. On failure, MESSAGE E with class ZMM_PR2RFQ.

Step 3 – Read requisitions (lcl_db_access->select_open_prs):

SELECT e~banfn, e~bnfpo, e~bsart, e~ekgrp, e~werks, e~matnr, e~matkl,
  e~txz01, e~menge, e~bsmng, e~meins, e~badat, e~lfdat
  FROM eban AS e
  INNER JOIN t001w AS w ON w~werks = e~werks
  INNER JOIN t001k AS k ON k~bwkey = w~bwkey
  WHERE e~ekorg = @is_sel-ekorg
  AND k~bukrs = @is_sel-bukrs
  AND e~bstyp = 'B'  AND e~loekz = @space AND e~ebakz = @space
  AND e~statu = 'N'  AND e~frgrl = @space AND e~blckd = @space
  AND e~pstyp <> '9'
  AND e~banfn IN @is_sel-r_banfn AND e~bsart IN @is_sel-r_bsart
  AND e~ekgrp IN @is_sel-r_ekgrp AND e~werks IN @is_sel-r_werks
  AND e~matnr IN @is_sel-r_matnr AND e~matkl IN @is_sel-r_matkl
  AND e~badat IN @is_sel-r_badat AND e~lfdat IN @is_sel-r_lfdat
  INTO TABLE @rt_prs.

Then DELETE rt_prs WHERE menge <= bsmng and compute open_qty = menge − bsmng. Empty result → MESSAGE S 010 DISPLAY LIKE 'I' and stop.

Step 4 – Read vendors (lcl_db_access->select_vendors): LFA1 (LIFNR, NAME1, SPERR, SPERM, LOEVM) WHERE lifnr IN s_lifnr; LFM1 (LIFNR, EKORG, SPERM, LOEVM) WHERE lifnr IN s_lifnr AND ekorg = p_ekorg. Stored in a HASHED table keyed by LIFNR.

Step 5 – Build output and groups (lcl_processor->build_groups): for each vendor × PR line, append one output row. Group key = LIFNR + EKGRP; each group becomes one RFQ. Sort by EKGRP, LIFNR, BANFN, BNFPO. In a test run without vendors, one row per PR line is shown with blank vendor and status Simulated.

Step 6 – Test run. Status icon = ICON_YELLOW_LIGHT, message 'Simulated – no RFQ created' (S 013). Go to step 9.

Step 7 – Update run, per group:

  • AUTHORITY-CHECK M_ANFR_EKG (EKGRP) and M_ANFR_WRK (each WERKS). Failure → lines red, E 012, next group.
  • Call io_creator->create_rfq( is_header = {bsart, ekorg, ekgrp, lifnr, angdt, spras} it_items = PR refs with open qty and LFDAT ) → ev_ebeln, et_return TYPE bapiret2_t.
  • lcl_rfq_creator_bdc implementation: builds BDCDATA for ME41 (initial screen: RFQ type, quotation deadline, purchasing org, purchasing group; Reference → Purchase requisition; select the PR items; vendor address screen with LIFNR; save). It then runs CALL TRANSACTION 'ME41' USING lt_bdc OPTIONS FROM ls_ctu (DISMODE 'N', UPDMODE 'S', DEFSIZE 'X') MESSAGES INTO lt_msg. Messages are converted to BAPIRET2 via MESSAGE_TEXT_BUILD-equivalent formatting (MESSAGE ID … INTO lv_text). The new RFQ number is taken from the success message variables; the exact screen numbers/fields and success message ID are recorded in SHDB during build (see Open Issues).
  • Post-check: SELECT SINGLE ebeln FROM ekko WHERE ebeln = @ev_ebeln AND bstyp = 'A' to confirm the document exists. On success all group lines get ICON_GREEN_LIGHT, EBELN and message S 011. On failure, ICON_RED_LIGHT and the first E/A message from et_return.
  • UPDMODE 'S' (synchronous) means each RFQ is committed by ME41 itself. No COMMIT WORK in the report, and no cross-group rollback; each RFQ is an independent LUW.

Step 8 – Counters. gv_lines (TYPE i), gv_rfq_ok (TYPE i), gv_err (TYPE i) for the header.

Step 9 – Display lcl_alv_view->display (see section 4).

Data model / hierarchy: EBAN (PR item) → T001W (plant → valuation area) → T001K (valuation area → company code); T024E (purchasing org → company code); T161 (RFQ type, BSTYP A); LFA1/LFM1 (vendor general / purchasing data); EKKO/EKPO (created RFQ; EKPO-BANFN/BNFPO hold the PR reference).

5 Assumptions in Technical Design

  • No RFQ-creation BAPI exists on this ECC release (verified in TFDIR), so ME41 batch input is the creation method.
  • One RFQ per vendor × purchasing group (standard competitive-bidding pattern; ME41 holds one vendor per RFQ).
  • PRs with processing status A (already referenced by an RFQ) are excluded to prevent duplicates, e.g. PR 0010048199.
  • Company code is derived through plant → valuation area (T001W/T001K), because EBAN has no company-code field.
  • Code is written for SAP_BASIS 740: new Open SQL syntax with @, inline declarations, no CDS/AMDP/REDUCE/enums.

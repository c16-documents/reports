2 Business Requirement

Buyers currently create a Request for Quotation (RFQ) by hand for each purchase requisition (PR) that needs sourcing. The customer wants this to happen automatically. A scheduled program must:

  • pick up released PRs,
  • create a new S/4HANA RFQ for them with up to 3 suppliers,
  • copy the PR's delivery dates and texts,
  • set the quotation deadline to 30 days after creation,
  • publish the RFQ so it reaches suppliers through SAP Ariba,
  • log every created, skipped and failed PR.

2.1 Business benefits

  • Removes manual RFQ creation effort for purchasing group 001.
  • Gives PR-to-RFQ turnaround of under 24 hours (daily run).
  • Applies consistent RFQ naming, deadline and supplier rules.
  • Keeps a full audit trail from PR to RFQ to Ariba event.

6.2 FR-02: Authorization filtering

The program processes only PR items for purchasing orgs, purchasing groups and plants the executing user (or job user) is authorised for, using the standard RFQ authorisation checks. Unauthorised items are skipped and logged.

6.3 FR-03: Purchasing organisation derivation

Standard SAP has no assignment from purchasing group to purchasing org. Purchasing groups are organisation-neutral, and in the current ECC landscape one plant (1000) is linked to 5 purchasing orgs. A small custom mapping table is therefore required.

SituationBehaviour
PR item has no purchasing orgRead mapping table ZMM_PRRFQ_ORGMAP by purchasing group (and optionally plant). Use the mapped org.
No mapping entry existsSkip the item. Error logged: "No purchasing org mapping for purchasing group &".
PR item has a purchasing orgKeep the PR value (D-15).
PR org differs from the mappingKeep the PR value and log a warning (D-15).
Mapped org not assigned to the plantSkip the item with an error. The RFQ would fail validation anyway.

The mapping table is maintained by the business through a standard maintenance view (SM30 or custom transaction), protected by authorisation and recorded in table change logs.

6.4 FR-04: Supplier (bidder) determination

  1. Supplier 1: the supplier on the PR item. Use the fixed supplier if filled, otherwise the desired supplier.
  2. Suppliers 2–3: source list entries for the same material, plant and purchasing org that are valid on the run date and not blocked in the source list. Entries marked as fixed source come first, then source list order. The supplier from step 1 and duplicates are excluded.
  3. Exclude suppliers blocked for purchasing (central or purchasing-org level) or for posting (central or company-code level), and suppliers marked for deletion (D-03).
  4. Exclude suppliers that are not enabled for SAP Ariba (no Ariba Network / Business Network ID mapping). See IP-03.
  5. Stop at a maximum of 3 suppliers (parameter, default 3).
  6. If 1 or 2 suppliers are found, create the RFQ anyway and log a warning (D-14).
  7. If 0 suppliers are found, skip the item and log an error.
  8. Text items (no material) have no source list, so only supplier 1 applies.

6.5 FR-05: RFQ creation and field mapping

Grouping

6.6 FR-06: Publish to SAP Ariba

  • After an RFQ is saved, the program runs the standard Publish step (parameter "Publish", default ON).
  • Publishing changes the RFQ status to Published and triggers the standard outbound RFQ message to SAP Ariba Sourcing (IP-02).
  • If publishing fails, the RFQ is kept unpublished, an error is logged and the buyer publishes it manually after correction. The RFQ is not deleted.

6.8 FR-08: Logging and output

  • ALV list with one row per PR item: status, PR/item, material, plant, purchasing group, purchasing org and its source (PR or mapping), suppliers 1–3, RFQ number, RFQ name, deadline, delivery date, publish status, message.
  • Application log (transaction SLG1, object/subobject to be defined) for every run, including background runs.
  • A persistent log table records each PR item → RFQ for audit and re-run protection.
  • Job spool contains the ALV list. An email summary to buyers is optional (OP-12).

12 Non-Functional Requirements

  • Volume: sized for up to several thousand PR items per run. Reads are done in bulk, with no database reads inside loops.
  • Runtime: target under 30 minutes per daily run.
  • Idempotency: a PR item is never converted twice. The checks are PR status, existing RFQ reference and the log table.
  • Restartability: a failed run can be restarted. Only unprocessed items are picked up.
  • Auditability: the log table plus application log are kept for 2 years (proposed).
  • Code Quality: RFQ creation and publishing use only released or standard interfaces, with no direct table updates. Custom logic stays in the customer namespace.

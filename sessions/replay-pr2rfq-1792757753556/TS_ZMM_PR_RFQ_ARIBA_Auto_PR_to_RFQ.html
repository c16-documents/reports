3.2 Validation of Selection Criteria

  • AT SELECTION-SCREEN ON S_EKGRP: must not be initial (E, ZMM_PRRFQ 002). Every single value must exist in T024 (E, 003).
  • AT SELECTION-SCREEN ON S_EKORG / S_WERKS: single values must exist in T024E / T001W (E, 004).
  • P_DLDAYS: 1–365 (E, 005).
  • P_MAXBID: 1–9. Business default 3 (E, 006).
  • Mapping completeness: for each purchasing group in S_EKGRP with no entry in ZMM_PRRFQ_ORGMAP, warning 007 (online only). Items needing derivation will be skipped.
  • Background check: if sy-batch = abap_true and P_TEST = abap_true, write info 008 to the log ("Job running in test mode – no RFQs created").
  • Authorisation: AUTHORITY-CHECK on M_ANFR_EKO (ACTVT 01) for each single EKORG value entered. Item-level checks are repeated during processing (3.4).
  • Run lock: at START-OF-SELECTION, ENQUEUE_EZMM_PRRFQ (exclusive, mode E, scope client). If foreign lock, E 009 and the run stops.

3.3 CDS Views/AMDP/Table Function

No custom CDS view, AMDP or table function is created. The program uses Open SQL reads (or released standard read views where available on the target, TBV). The selection and join logic is documented below because it defines the data model.

3.3.1 Selection Condition

  • EBAN (PR items): EKGRP IN s_ekgrp, EKORG IN s_ekorg, WERKS IN s_werks, BSART IN s_bsart, BANFN IN s_banfn, MATKL IN s_matkl, BADAT IN s_badat.
    • Not deleted: LOEKZ = space.
    • Not closed: EBAKZ = space.
    • Released: FRGRL = space (release complete or not subject to release; OP-02).
    • Open: STATU = 'N' (not yet processed; TBV on S/4), EBELN = space, KONNR = space.
    • Open quantity: MENGE − BSMNG > 0.
    • Item category: PSTYP IN lr_pstyp (default standard '0' only; OP-04).
  • ZMM_PRRFQ_LOG: exclude BANFN/BNFPO with STATUS IN ('C','P'), i.e. RFQ created or published.
  • EKPO (existing RFQ): exclude PR items already referenced by an RFQ item: EKPO-BANFN/BNFPO with EKKO-BSTYP = 'A' and LOEKZ = space.
  • EORD (source list): MATNR/WERKS FOR ALL ENTRIES of PR items (driver checked not initial, R-RT09). VDATU ≤ sy-datum ≤ BDATU, NOTKZ = space (not blocked), EKORG = derived org or space.
  • Supplier checks: LFA1 (SPERM purchasing block, SPERR posting block, LOEVM deletion flag), LFM1 (SPERM per EKORG), LFB1 (SPERR per BUKRS). Fields to be verified via DD03L on the target before coding.

3.3.2 Join Condition

  • EBAN → ZMM_PRRFQ_ORGMAP: EBAN-EKGRP = ORGMAP-EKGRP (AND ORGMAP-WERKS = EBAN-WERKS or ORGMAP-WERKS = space, plant-specific entry first).
  • EBAN → T001W → T001K: EBAN-WERKS = T001W-WERKS; T001W-BWKEY = T001K-BWKEY (gives BUKRS).
  • Derived org check: T024W-WERKS = EBAN-WERKS AND T024W-EKORG = derived org.
  • EBAN → EORD: EBAN-MATNR = EORD-MATNR AND EBAN-WERKS = EORD-WERKS.
  • Bidder → LFA1 / LFM1 (LIFNR + EKORG) / LFB1 (LIFNR + BUKRS).
  • EBAN → EKPO/EKKO: EKPO-BANFN = EBAN-BANFN AND EKPO-BNFPO = EBAN-BNFPO; EKKO-EBELN = EKPO-EBELN AND EKKO-BSTYP = 'A'.

3.4.3 Procedure

For each candidate PR item, after org derivation, the program runs AUTHORITY-CHECK on M_ANFR_EKO (EKORG = derived org, ACTVT 01), M_ANFR_EKG (EKGRP) and M_ANFR_WRK (WERKS). If sy-subrc ≠ 0, the item is skipped with E 020 "No authorisation to create RFQ for org &1 / group &2 / plant &3".

The job user gets a dedicated role, e.g. Z_MM_PRRFQ_BATCH, containing the values above for the scoped orgs. Key users get Z_MM_PRRFQ_MAP for mapping maintenance.

3.7 Processing Logic

Data model: PR item (EBAN) 1:n source list entries (EORD) per material/plant. PR item n:1 RFQ group. RFQ group 1:n bidders (max 3). PR item 1:1 log record per run.

  1. INITIALIZATION: default S_BADAT = sy-datum − 30 … sy-datum. Default S_EKGRP = 001 and S_BSART = NB.
  2. START-OF-SELECTION – init: lock the run (ENQUEUE_EZMM_PRRFQ; on foreign lock, E 009 and stop). Generate RUN_ID (cl_system_uuid). Create BAL log (object ZMM / sub PRRFQ, extnumber = RUN_ID).
  3. select_pr_items: one SELECT on EBAN with the criteria in 3.3.1, into typed table gt_pr. If initial, S 010 "No eligible PR items found" and end the run normally (log saved).
  4. exclude_processed: read ZMM_PRRFQ_LOG (STATUS C/P) and EKPO/EKKO RFQ references for gt_pr keys (FOR ALL ENTRIES, driver checked not initial). Delete matches from gt_pr. Count logged as I 011.
  5. derive_purch_org: read ZMM_PRRFQ_ORGMAP (ACTIVE = X) into a hashed table keyed by EKGRP + WERKS. Per item:
    • EKORG initial: look up (EKGRP, WERKS), then (EKGRP, space). If found, set EKORG and ORG_SOURCE = 'M'. Otherwise status S, E 012.
    • EKORG filled: ORG_SOURCE = 'P'. If a mapping exists and differs, W 013 (D-15).
    • Check T024W (plant ↔ org). If no assignment, E 014 and skip.
  6. derive_company_code: T001W-BWKEY → T001K-BUKRS per plant (buffered hashed table).
  7. check_authority: per item, see 3.4.3. Skip with E 020.
  8. determine_bidders: bulk-read EORD, LFA1, LFM1, LFB1 for all candidate suppliers. Per item:
    • Supplier 1 = FLIEF, otherwise LIFNR.
    • Candidates 2..n = EORD entries (same MATNR / WERKS, EKORG = derived or space, valid on sy-datum, NOTKZ = space), sorted FLIFN DESC, ZEORD ASC.
    • Remove duplicates and supplier 1.
    • Remove blocked suppliers: LFA1-SPERM / SPERR / LOEVM, LFM1-SPERM (EKORG), LFB1-SPERR (BUKRS). W 015 per supplier.
    • Remove suppliers not Ariba-enabled (is_ariba_enabled, OP-13; TBV source). W 016.
    • Take the first P_MAXBID.
    • 0 suppliers: status S, E 017.
    • Fewer than P_MAXBID: W 018 (D-14).
    • Text item (MATNR initial): supplier 1 only.
  9. group_items: build group key = BANFN + EKORG + EKGRP + BUKRS + sorted bidder list (concatenated). Assign items to groups (sorted table gt_group).
  10. Test mode branch: if P_TEST = X, fill the simulated RFQ name ("SIMULATION"), deadline and status 'T' (test), display the ALV and stop. No commit and no log table write; the BAL log is saved for traceability.
  11. create_rfq per group (released RFQ BO via EML; entity, field and action names TBV on target):
    • Header: RFQ type, company code, purchasing org, purchasing group, currency.
    • RFQ name = build_rfq_name: 'RFQ' + timestamp (YYYYMMDDhhmmss of run start, system time zone) + '-' + run counter (2 digits, incremented per RFQ).
    • Quotation latest submission date = sy-datum + P_DLDAYS (date guard R-RT03).
    • Items: create-by-association, with PR reference (BANFN/BNFPO), material, short text, material group, plant, storage location, open quantity (MENGE − BSMNG), unit, delivery date = LFDAT, account assignment (EBKN) when KNTTP ≠ space.
    • Bidders: create-by-association, 1–3 suppliers.
    • Delivery date check: if LFDAT < deadline, W 019.
    • MODIFY ENTITIES … FAILED / REPORTED, then COMMIT ENTITIES (one LUW per RFQ group).
    • If failed / reported errors: ROLLBACK ENTITIES, status E for all group items, E 021 + BO messages to BAL. Continue with the next group.
    • Read back the RFQ number (late numbering mapping from COMMIT ENTITIES … MAPPED / CONVERT KEY, TBV).
  12. copy_texts: READ_TEXT on the PR header (object EBANH, id B01) and items (object EBAN, ids per text determination). Append the standard header text (SO10 text, name from constant / OP-10). Write to RFQ header and item text entities in the same create call where the BO supports text associations (TBV). Otherwise use SAVE_TEXT on the RFQ text objects after commit. Missing text is not an error (no message).
  13. publish_rfq: if P_PUBL = X, EXECUTE the Publish action on the created RFQ, then COMMIT ENTITIES. Success: status P, S 022. Failure: status F, E 023 + BO messages. The RFQ is kept. The output to Ariba is raised by standard output determination on publish (IP-02); the program does not call the outbound service directly.
  14. write_log: INSERT ZMM_PRRFQ_LOG rows for all processed/skipped items (per group, after the RFQ commit, in the same LUW as the next commit or via a separate COMMIT WORK). BAL_LOG_MSG_ADD for every message with context (BANFN/BNFPO).
  15. END-OF-SELECTION: BAL_DB_SAVE. Display ALV (online or spool). Summary message S 024 "&1 RFQs created, &2 published, &3 items skipped, &4 errors". DEQUEUE_EZMM_PRRFQ.

Performance: no SELECT inside loops. All reads are bulk with FOR ALL ENTRIES (driver not initial) into hashed tables. Packages of 100 RFQs per commit are not needed because there is one commit per RFQ. Expected volume is low (one purchasing group).

Coding rules: local classes only (no FORM). Typed DDIC structures. Every SELECT uses the same Open SQL syntax style. Every arithmetic and date operation has a guard. No direct UPDATE on EBAN or EKKO; PR status is updated by the RFQ BO through the PR reference.

5 Assumptions in Technical Design

  1. The target is S/4HANA on-premise or RISE Private Cloud 2022+ with classic extensibility (OP-00).
  2. A released RFQ business object or API supports create (header, items with PR reference, bidders, texts) and the Publish action on the target release (TBV). Fallback: RFQ OData API called locally.
  3. The Ariba Sourcing integration is live (D-11). Publishing triggers the outbound message through standard output determination, so no custom outbound call is needed.
  4. "001" is purchasing group 001 (D-13). "Keep them and warn" means the existing PR purchasing org is kept with a warning when it differs from the mapping (D-15).
  5. "Released only" is implemented as release indicator complete (FRGRL = space). PRs without a release strategy are included unless OP-02 decides otherwise.
  6. RFQ name uses the system time zone and a run counter suffix for uniqueness. The name fits the RFQ name field length (≤ 40 characters, TBV).
  7. Deadline = creation date + 30 calendar days.
  8. Standard RFQ defaulting provides payment terms and Incoterms. "Standard terms" are attached as a standard header text.
  9. Field names of EBAN / EORD / LFA1 / LFM1 / LFB1 listed in 3.3 are verified via DD03L on the target before coding.
  10. Daily volume for purchasing group 001 is low (hundreds of items). No parallel processing is required.

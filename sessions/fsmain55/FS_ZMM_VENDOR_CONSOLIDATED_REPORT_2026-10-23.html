2 Business Purpose

The report gives Procurement, Vendor Master Data and Compliance teams one consolidated view of vendor master data. The data would otherwise be spread across several transactions (XK03/MK03/FK03, BP, address maintenance and custom compliance tables). For each vendor it combines:

  • General vendor data (name, city, account group, created on/by, search term, VAT and tax numbers, industry, authorisation group, telephone, train station)
  • The customer-specific vendor attributes held in LFA1 (PO/Non-PO vendor, high-risk vendor code, risk category, e-invoice flag)
  • Address data (country, street lines 1–4, postal code, region, e-mail, and the "peol SPOC ID" held in the address remark)
  • Commercial data (payment terms from company code data, order currency from purchasing data)
  • Business Partner relationships (Group Vendor / Group Customer from BP relationships)
  • Compliance attributes: blocked status, blacklisting (ZVENDOR_BLOCK), MSME certificate number (ZMM_VENDOR_MSME) and BEE level (ZMM_VENDOR_BEE)

By default the report covers only the vendor account groups in scope for the business. These are kept in the TVARVC selection variable ZMM_VEND_ACC_GROUP (24 groups originally, plus one added under ChaRM 4000006474).

7 Processing Logic

7.1 Step 1 – Account group scope

If Vendor Account Group (S_KTOKK) is left blank, the program reads all TVARVC entries for variable ZMM_VEND_ACC_GROUP into S_KTOKK, so only the in-scope groups are reported. If the variable is missing, it stops with error V2.

7.2 Step 2 – Vendor selection (LFA1)

Vendors are read from LFA1 for the account groups in scope, with the additional restriction from whichever primary or secondary filter was entered:

FilterAdditional LFA1 condition
S_ERDATERDAT within range
S_LIFNRLIFNR within range
P_STATUS = INACTIVESPERR = 'X' OR SPERM = 'X' OR SPERQ = '03' OR SPERQ = '99'
P_STATUS = ACTIVESPERR ≠ 'X' AND SPERM ≠ 'X' AND SPERQ ≠ '99'
P_BLACK = Yes / NoVendor is / is not flagged VFLAG = 'X' in ZVENDOR_BLOCK
P_BEGRU = Yes / NoBEGRU = / ≠ 'HRV1'
P_BEGRU1 = Yes / NoBEGRU = / ≠ 'RPTY'
P_BRSCH = Yes / NoBRSCH = / ≠ '0041'

7.3 Step 3 – Group Vendor flow (S_GVEND entered)

The program reads BUT050 relationships where PARTNER2 is in S_GVEND, then all relationships of those group partners. It takes the related PARTNER1 numbers, reads them as customers (KNA1, KTOKD in S_KTOKK) and as vendors (LFA1, KTOKK in S_KTOKK), and applies the chosen secondary filter. Each related partner appears in the output as the vendor row, with the group partner shown as Group Vendor.

7.4 Step 4 – Enrichment, for each vendor

  • BP / Group: vendor → CVI_VEND_LINK (BP GUID) → BUT000 (BP number) → BUT050 (PARTNER1 = BP) gives Group Vendor (PARTNER2) and Group Customer.
  • Address: ADRC by LFA1-ADRNR gives country, street, supplements 1–3, postal code and region. ADR6 gives the e-mail. ADRCT-REMARK gives the "peol SPOC ID".
  • Commercial: LFB1-ZTERM gives payment terms and LFM1-WAERS gives currency (first record found).
  • Compliance: ZMM_VENDOR_MSME gives the MSME certificate number and ZMM_VENDOR_BEE gives the BEE level.

7.5 Step 5 – Derived fields

Output fieldRule
Status'BLOCKED' if LFA1-SPERR = 'X' or SPERM = 'X' or SPERQ = '03' or SPERQ = '99'; otherwise blank
Blacklisted'BLACKLISTED' if ZVENDOR_BLOCK-VFLAG = 'X' for the vendor; otherwise blank

7.6 Step 6 – Output

If at least one row was built, the ALV grid is shown. If not, the program stops with error V3.

9 Authorisation

SECURITY: The program has no AUTHORITY-CHECK statements. Anyone who can run it sees vendor master data, including tax numbers, bank-adjacent compliance data and blacklist status, for every account group in scope. Recommendation: add checks on F_LFA1_GRP (account group, activity 03), F_LFA1_BEK (authorisation group LFA1-BEGRU, activity 03), and optionally F_LFA1_BUK / M_LFM1_EKO for the company-code and purchasing data. Assign a dedicated transaction code with S_TCODE.

12 Technical Notes / Code Quality

  • Uses classic TABLES and TYPE-POOLS statements, REUSE_ALV_GRID_DISPLAY (SLIS) and VRM_SET_VALUES. These are classic APIs (Level B) and remain compatible on ECC and on S/4HANA on-premise.
  • Reads LFA1 directly. On S/4HANA, LFA1 is still a transparent table filled through CVI from the Business Partner, but LFA1 fields such as SPERQ should be checked during conversion.
  • Already uses CVI_VEND_LINK / BUT000 / BUT050, so it is BP-aware.
  • In the program, the custom data elements for append fields and Z-table fields are commented out and replaced with CHAR20. Labels therefore come only from the field catalog texts.
